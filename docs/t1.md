# T1. Сравнительный анализ генераторов статических сайтов

Рассмотрены четыре генератора: **MkDocs + Material**, **Sphinx + MyST-Parser**, **Pelican** (обязательные)
и **Quarto** (по выбору). Первые три проверены на практике в задании [P2](p2.md) и в тесте масштаба
ниже. Quarto оценён по документации и опыту использования, в P2 не собирался — его оценки помечены
как «по документации».

!!! info "Версии"
    MkDocs 1.6.1, Material 9.7.7, mkdocs-bibtex 4.4.0; Sphinx 9.1.0, MyST-Parser 5.1.0,
    sphinxcontrib-bibtex 2.7.0, sphinx-design 0.7.0, Furo 2025.12.19; Pelican 4.12.0;
    Quarto 1.x (по документации, не устанавливался). Python 3.14.2.

## Шкала и веса

Оценка по каждому критерию — от 0 до 3:

| Балл | Значение |
|---:|---|
| 0 | Нет и разумно не реализуется |
| 1 | Только через сторонний плагин, ручной HTML или с существенными ограничениями |
| 2 | Работает с настройкой или поддерживаемым плагином, ограничения несущественны |
| 3 | Из коробки и полноценно |

**Обоснование весов** для задачи «публикация результатов экспериментов»:

- **Научный контент — 49 из 100.** Это смысл задачи. Тяжелее всего весят то, без чего отчёт
  об эксперименте неполон или невоспроизводим: формулы со ссылками (9), исполняемый контент с
  кэшированием (9) — результаты должны пересчитываться из данных, а не вставляться руками, — и
  библиография (9).
- **Вёрстка — 17.** PDF из того же источника (6) нужен для сдачи статьи или отчёта; дизайн,
  шаблоны и колонки (4 + 4 + 3) важны, но вторичны.
- **Эксплуатация — 34.** Зрелость и лицензия (6) и порог входа (7) определяют, переживёт ли сайт
  следующий семестр. Версионирование и автодокументирование весят мало (по 3): у результатов
  эксперимента нет «версий API».

## Скорость сборки на масштабе

Одна страница P2 собирается за доли секунды, и разница определяется запуском интерпретатора.
Поэтому сборка дополнительно измерена на синтетическом корпусе (`scripts/scale_test.py`):
300 страниц с формулой, таблицей и листингом.

--8<-- "_generated/scale.md"

Выводы:

- **MkDocs** не умеет инкрементальную сборку: правка одной страницы стоит столько же, сколько
  холодная сборка. Объём результата растёт квадратично: в каждую из 300 страниц вшито полное
  меню из 300 пунктов (29 МБ против 11–15 МБ у остальных).
- **Sphinx** в холодном режиме самый медленный (в 6 раз медленнее MkDocs), но после правки одной
  страницы пересобирается за 0,5 с благодаря кэшу doctree. Для живого `sphinx-autobuild` это
  важнее холодного времени.
- **Pelican** самый быстрый, но сравнение не совсем честное: без плагина для формул его
  Markdown-обработка проще.

## Вывод T1

Для публикации результатов экспериментов на Python оптимален **Sphinx + MyST-Parser** (с myst-nb
для исполняемых ноутбуков и sphinxcontrib-bibtex). Только он закрывает весь научный набор на
этапе сборки и из коробки: нумерация и ссылки на формулы, рисунки и таблицы между документами,
библиография, PDF через LaTeX, русский стемминг. При этом проект зрелый и под свободной лицензией.
Плата за это — самый высокий порог входа и самая медленная холодная сборка.

**Quarto** отстаёт ненамного: 83 против 87. По научному контенту он равен Sphinx, а проигрывает на
эксплуатации — поиске, версионировании и зрелости экосистемы под Python.
